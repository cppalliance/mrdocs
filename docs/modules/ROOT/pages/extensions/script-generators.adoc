= Script Generators

A *script generator* is the second kind of Mr.Docs extension driven by scripts. This covers the cases where customizing xref:extensions/handlebars-extensions.adoc[Handlebars templates] is not enough to express the output format. A generator hands the whole emit to the script instead.

[NOTE]
====
A generator is written and loaded exactly like a xref:extensions/corpus-transforms.adoc[corpus transform]: a `.js` or `.lua` script under `extensions/` in an xref:configuration/output.adoc#addons[addon directory], handed the same `ctx`. It declares itself with `mrdocs.register_generator(id, fn)` instead of `mrdocs.register_transform`. The `id` is the name you select on the command line with `--generator=<id>`; a registered generator takes precedence over a built-in of the same name.
====

== Outputting the corpus

The smallest useful generator hands the corpus straight to `JSON.stringify`. A complete, runnable example lives at `examples/generators/script-driven/json/`. Given this input:

.`simple.cpp`
[source,cpp]
----
include::example$examples/generators/script-driven/json/simple.cpp[]
----

In very few lines of code, this extension declares a `json` generator that writes every symbol to a single `reference.json`:

.`addons/extensions/json.js`
[source,js]
----
include::example$examples/generators/script-driven/json/addons/extensions/json.js[]
----

Select it with `--generator=json`. Because `ctx.corpus.symbols` is already plain data, the whole generator is one `JSON.stringify` call, and the shape is yours: `map` or `filter` the array, or read `ctx.params` to add options, before writing it. A script generator takes precedence over a built-in of the same name, so this replaces the built-in xref:generators/json.adoc[JSON generator], which is the same idea implemented in C++.

The output is an array of every symbol, each a full DOM object as seen by the templates, with parent/child relationships expressed as `id` references. Its first entry, the global namespace, begins (the file continues with one object per symbol):

.`reference.json` (excerpt)
[source,json]
----
include::example$examples/generators/script-driven/json/reference.json[lines=1..45]
----

== Navigation lists

A navigation list over the whole API is the same idea as the search index, an artifact aggregated across every symbol, but it emits a nested list instead of JSON objects. Deriving it from the corpus prevents a project from manually maintaining a separate nav partial and re-syncing it whenever the API changes. A complete, runnable example lives at `examples/generators/script-driven/toc/`:

[tabs]
======
Generator::
+
.`addons/extensions/toc.js`
[source,js]
----
include::example$examples/generators/script-driven/toc/addons/extensions/toc.js[]
----

Input::
+
.`simple.cpp`
[source,cpp]
----
include::example$examples/generators/script-driven/toc/simple.cpp[]
----

Config::
+
.`mrdocs.yml`
[source,yaml]
----
include::example$examples/generators/script-driven/toc/mrdocs.yml[]
----
======

The generator walks the namespace tree once, then serializes it to three formats from that single walk, so the nav for each output stays in step. The corpus is a tree: the global namespace is the one symbol with no `parent`, and a namespace lists its children in `members`, grouped by category (`namespaces`, `records`, `enums`, `functions`, ...). The walk descends through namespaces and treats every record, enum, and function as a leaf linking to its own page. Select it with `--generator=toc`; it writes one file per format:

[tabs]
======
Markdown::
+
.`toc.md`
[source,markdown]
----

----

AsciiDoc::
+
.`toc.adoc`
[source,asciidoc]
----
include::example$examples/generators/script-driven/toc/toc.adoc[]
----

HTML::
+
.`toc.html`
[source,html]
----
include::example$examples/generators/script-driven/toc/toc.html[]
----
