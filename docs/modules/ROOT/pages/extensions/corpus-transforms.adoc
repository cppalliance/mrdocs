= Corpus Transforms

A *corpus transform* is a pipeline extension that rewrites metadata across many symbols at once to incorporate project conventions into the corpus. You can use it to do things like:

* Backfill documentation fields from naming conventions,
* Create and identify relations between fields,
* Tag symbols by group, and
* Mark generated code as "implementation defined" according to project conventions.

Transforms run once, after the corpus is built and finalized and before any generator runs, so every output format sees the change. After a transform runs, the corpus forgets the lookups by name it remembered, so the generators see a symbol that a transform renames under its new name.

[NOTE]
====
As specified in xref:page$extensions/defining-extensions.adoc[], you can write an extension in Lua, JavaScript, or {cpp}. A transform must be independent and not rely on the order in which extensions are executed.
====

Every transform works on the same corpus. The transforms run one after another, and each sees what the earlier ones wrote. Each receives its own xref:configuration/reference.adoc#transform-options_option[`transform-options`]`.<id>` block. The transforms of scripts and of plugins run in one pipeline. There is nothing to select: once a plugin is xref:extensions/defining-extensions.adoc#installing-a-plugin[installed], its transform runs in every build.

The function body is where the work goes, and the sections below fill it in. The {cpp} tabs of the later sections show the callable a plugin passes to cpp:PluginContext::registerTransform[registerTransform] and the helpers it uses.

=== The context

Every transform registered as a function receives a cpp:TransformExtensionContext[], which holds the corpus, the configuration, the transform's own options block and the reporter. A plugin receives the object itself. A script receives a proxy of it as `ctx`, whose keys are the fields of the object (`ctx.corpus`, `ctx.config`, `ctx.params`, `ctx.report`), as xref:extensions/defining-extensions.adoc#input-parameters[Defining Extensions] says.

The rest of this page uses the corpus: in a script a flat view that the sections below walk and change, and in {cpp} the cpp:Corpus[] itself, a range of cpp:Symbol[] objects.

=== Errors

An error from a transform stops the run before any generator sees the corpus. The diagnostic names the transform by its id. Here a script transform registered as `brief-filler` reads `transform-options.brief-filler.text` and raises because the block has no `text`:

[source,text]
----
the transform "brief-filler" failed: [script]:2: transform-options.brief-filler.text is missing
----

=== Emitting warnings

A read-only transform can do more than compute totals: it can report the problems it finds through `ctx.report`, the reporter of the run.

A script calls `ctx.report.warn(...)`, `ctx.report.error(...)` or `ctx.report.info(...)` with the same free-form arguments as `console.log`. A plugin calls `ctx.report->warn(...)` and the others with a format string and its arguments, as `std::format` takes them. Either way, Mr.Docs counts each message in the totals of the run like one of its own, and under xref:configuration/reference.adoc#warn-as-error_option[`warn-as-error`] a warning counts as an error.

=== Corpus shape invariants

What a transform changes has to leave the corpus in the shape finalization left it in:

* A symbol keeps its id and its kind.
* Every symbol id written into the corpus names a symbol the corpus has, so a transform cannot create or destroy a symbol.
* A transform does not redo what finalization derived: sorted member lists, overload sets, copied briefs and resolved references.

Within those limits a transform changes what it likes: doc comments, attributes, and which members a list holds and in what order.

[#reading-files]
== Reading files

After being presented with the xref:index.adoc#why-generate-from-source[arguments for generated reference documentation], a common objection is that the prose should be mostly written by technical writers, not developers. The rationale is not to clutter the headers, and that technical writers can focus on use cases the users are interested in and dedicate themselves to long tutorials.

A transform can bridge the two by also reading documentation from external sources. While developers write documentation in code that is verifiably correct and guaranteed never to drift, a writer keeps the extra documentation alongside the project. The ghostwrite transform fills in each symbol's description from the corresponding file. A complete, runnable example lives at `examples/extensions/ghostwriter/`.

The code includes a brief for each symbol and its metadata, while the writer provides a longer description. The `mrdocs.yml` configuration file loads the transform and points it at the source directory through xref:configuration/reference.adoc#transform-options_option[`transform-options`]`.ghostwriter.source`.

The transform reads the file whose path matches each symbol's scope and sets its description from the file's paragraphs. It only touches the description, and every other field the developer wrote stays. The `distance` function shows the split: its brief, its `@param` entries, and its `@return` all come from the header, while the writer's file supplies just the longer description.
