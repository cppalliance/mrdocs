= Programmatic Generators
:page-aliases: extensions/script-generators.adoc
:url-plugins: https://github.com/cppalliance/mrdocs/tree/{page-origin-refname}/examples/extensions

A *programmatic generator* is the kind of pipeline extension that owns the whole emit. In a script it writes files through `ctx.output`, and in {cpp} it implements cpp:Generator::build[]. Either way it decides which files exist and what goes in them, instead of rendering one page per symbol.

[TIP]
====
A xref:extensions/data-driven-generators.adoc[data-driven generator] is the other kind of custom generator: a directory of Handlebars templates and a manifest define it, and code does not. Reach for a programmatic generator when customizing xref:extensions/handlebars-extensions.adoc[templates] is not enough to express the output format.
====

[#registering-a-generator]
== Registering a generator

A generator is written and loaded like a xref:extensions/corpus-transforms.adoc[corpus transform], as xref:extensions/defining-extensions.adoc#registering-an-extension[Defining Extensions] describes. A script registers it with `mrdocs.cpp:PluginContext::registerGenerator[register_generator](id, fn)` and a plugin registers it with cpp:PluginContext::registerGenerator[registerGenerator]:

[tabs]
======
JavaScript::
+
.`addons/extensions/hello_world_generator.js`
[source,javascript]
----
include::example$examples/extensions/hello-world-generator/js/extensions/hello_world_generator.js[]
----

Lua::
+
.`addons/extensions/hello_world_generator.lua`
[source,lua]
----
include::example$examples/extensions/hello-world-generator/lua/extensions/hello_world_generator.lua[]
----

{cpp}::
+
.`hello-world-generator/plugin.cpp`
[source,cpp]
----
include::example$examples/extensions/hello-world-generator/plugin/plugin.cpp[tag=plugin,indent=0]
----
======

A generator registered as a function receives a cpp:GeneratorExtensionContext[]. It holds the corpus, the configuration, the output path, the options block and the reporter of the run.

[NOTE]
====
The rules for generator `id`s:

* Its block of options is xref:configuration/reference.adoc#generator-options_option[`generator-options.<id>`].
* You select it on the command line with `--generator=<id>`.
* It must differ from the id of every other generator, built-in or not, or Mr.Docs stops the run with `generator id="<id>" already exists`.
====

The generator receives the corpus and writes whatever it wants into the output directory. The examples above write one file. A script writes it with the helper `ctx.output.write(path, text)`, a function the script binding adds to the context, as it does `ctx.stringify` and the functions of `ctx.report`.

Once a plugin is xref:extensions/defining-extensions.adoc#installing-a-plugin[installed], its generator is selectable like any other, through the xref:configuration/reference.adoc#generator_option[`generator`] option:

[source,yaml]
----
generator: hello-world-generator
----

A generator class gets its xref:configuration/reference.adoc#generator-options_option[`generator-options.<id>`] block from cpp:getGeneratorParams[], which it calls from cpp:Generator::build[]. The block is an empty object when the configuration sets none.

[#outputting-the-corpus]
== Outputting the corpus

The smallest useful generator hands the corpus straight to `JSON.stringify`. A complete, runnable example lives at `examples/generators/script-driven/json/`. Given this input:

.`simple.cpp`
[source,cpp]
----
include::example$examples/generators/script-driven/json/simple.cpp[]
----

In very few lines of code, this extension declares a `symbols-json` generator that writes every symbol to a single `reference.json`:

.`addons/extensions/json.js`
[source,js]
----
include::example$examples/generators/script-driven/json/addons/extensions/json.js[]
----

Select it with `--generator=symbols-json`. Because `ctx.corpus.symbols` is already plain data, the whole generator is one `JSON.stringify` call, and the shape is yours: `map` or `filter` the array, or read `ctx.params` to add options, before writing it. The id has to be new: a generator whose id is taken, by a built-in generator or by another extension, is refused, so this one cannot be called `json`, the id of the built-in xref:generators/json.adoc[JSON generator], which is the same idea implemented in C++.

The output is an array of every symbol, each a full DOM object as seen by the templates, with parent/child relationships expressed as `id` references. Its first entry, the global namespace, begins (the file continues with one object per symbol):

.`reference.json` (excerpt)
[source,json]
----
include::example$examples/generators/script-driven/json/reference.json[lines=1..45]
...
----

=== Symbol selection

An index does not list every entry of the corpus. The fields that decide what to keep are on cpp:Symbol[]. Its extraction mode (cpp:ExtractionMode[]) says whether it is shown, which `regular` and `see-below` symbols are. Its inherited-from id marks a copy of a base class member, and an overload set has its own kind and members.

== Table of Contents

A table of contents or a navigation list over the whole API is the same idea as the search index: an artifact aggregated across every symbol, but it emits a nested list instead of JSON objects. Deriving it from the corpus prevents a project from manually maintaining a separate nav partial and re-syncing it whenever the API changes. A complete, runnable example lives at `examples/generators/script-driven/toc/`:

[tabs]
======
Generator::
+
.`addons/extensions/toc.js`
[source,js]
----
include::example$examples/generators/script-driven/toc/addons/extensions/toc.js[]
----

Input::
+
.`simple.cpp`
[source,cpp]
----
include::example$examples/generators/script-driven/toc/simple.cpp[]
----

Config::
+
.`mrdocs.yml`
[source,yaml]
----
include::example$examples/generators/script-driven/toc/mrdocs.yml[]
----
======

The generator walks the namespace tree once, then serializes it to three formats from that single walk, so the nav for each output stays in step. The corpus is a tree: the global namespace is the one symbol with no `parent`, and a namespace lists its children in `members`, grouped by category (`namespaces`, `records`, `enums`, `functions`, ...). The walk descends through namespaces and treats every record, enum, and function as a leaf linking to its own page. Select it with `--generator=toc`; it writes one file per format:

== Reflection Generators

A custom generator does not have to emit documentation. It could be used for any task related to the project's public API and even write back to the files used to generate the Corpus. For instance, https://www.boost.org/doc/libs/release/libs/describe/[Boost.Describe^] adds compile-time reflection to C++ types, but its `BOOST_DESCRIBE_STRUCT` and `BOOST_DESCRIBE_ENUM` annotations are hand-written. The corpus already knows every type and its members, so the same walk that produces docs can emit those annotations to keep them in sync with the code. A complete, runnable example lives at `examples/generators/script-driven/describe/`:

In the example, for `circle.hpp` it writes `circle.described.hpp`, which includes `circle.hpp` and then the annotations for the types that header declares, including the annotations for the base class. A project can include the sidecar wherever it wants reflection over that header's types. Select it with `--generator=describe`:

== Round-trip extensions

An extension can register a transform and a generator together, so one addon covers both directions of the same job. For instance, a common task in C++ projects is keeping documentation examples and standalone snippet files in sync:

* *Import example snippets* from test or example files into the documentation comments when they are complex enough to be kept in a separate file, typically because they need special setup or teardown code to compile and run.
* *Exporting snippets* from documentation comments to testable source files when the snippets are short enough to be written inline.

In the extension:

* A corpus *transform* script can read example files and inject their snippets into the matching symbol's docs.
* A *generator* script can write every `@code` example out to a file the build can compile, so an example in a comment is broken.

An extension that implements both can keep the two in sync: the generator exports snippets from the docs to files if they weren't t included by the transform function.

[tabs]
======
Extension::
+
.`addons/extensions/snippets.lua`
[source,lua]
----
include::example$examples/generators/script-driven/snippets/addons/extensions/snippets.lua[tag=extension]
----
+
The helpers that read the example files, extract and dedent the snippets, fingerprint them and convert values are in the full file, https://github.com/cppalliance/mrdocs/tree/{page-origin-refname}/examples/generators/script-driven/snippets/addons/extensions/snippets.lua[`snippets.lua`^].

Headers::
+
[tabs]
=====
arithmetic.hpp::
+
[source,cpp]
----
include::example$examples/generators/script-driven/snippets/include/arithmetic.hpp[]
----

text.hpp::
+
[source,cpp]
----
include::example$examples/generators/script-driven/snippets/include/text.hpp[]
----
=====

Example file::
+
.`example-code/arithmetic.cpp`
[source,cpp]
----
include::example$examples/generators/script-driven/snippets/example-code/arithmetic.cpp[]
----

Config::
+
.`mrdocs.yml`
[source,yaml]
----
include::example$examples/generators/script-driven/snippets/mrdocs.yml[]
----
======

In the input, `add` keeps its example inline in the header comment, while `multiply` and `subtract` import theirs from a separate example file. The transform reads its inputs from `transform-options.snippets.source`, and the generator writes the inline snippets to `generator-options.snippets.output`. The rendered page then shows every example regardless of where it came from:

[.adoc-preview]
========
include::example$examples/generators/script-driven/snippets/reference.adoc[]
========

Export runs comments into files, and writes complete translation units, one per header. Each file includes its header and a small prelude, gives every symbol a function that runs its snippets (each in its own scope when there is more than one), and ends with a `main` that calls them all, so the file both compiles and runs as a test. It exports only the examples written inline in the headers. It leaves out the ones the transform imported, since they already live in a file the build compiles. `exported/arithmetic.cpp` therefore holds only `add`, not the imported `multiply` and `subtract`:

.Exported test files
[tabs]
======
exported/arithmetic.cpp::
+
[source,cpp]
----
include::example$examples/generators/script-driven/snippets/exported/arithmetic.cpp[]
----

exported/text.cpp::
+
[source,cpp]
----
include::example$examples/generators/script-driven/snippets/exported/text.cpp[]
----
======

Knowing which examples to skip is where the two halves of the extension meet. The transform function records a fingerprint of each snippet, and the generator reads that same table to skip them.

[TIP]
====
This extension can also compose with the xref:extensions/corpus-transforms.adoc#reading-files[ghostwriter transform]. A typical problem with technical writers is that their examples are only tested locally, so they can drift and break as the API moves. This extension would ensure these import snippets are also tested as inline scripts.
====
